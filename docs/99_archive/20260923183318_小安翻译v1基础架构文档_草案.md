## 1. 目标与边界

首版完成“输入文字 → 识别或选择语言 → 准备离线模型 → 翻译 → 复制、分享或朗读 → 本地历史与收藏”的闭环。无需账号、自建翻译服务、广告、支付、相机和麦克风权限。学习体验仅保留历史搜索与收藏回看，不引入课程、生词本、打卡系统。

本方案明确纳入 **go_router** 和 **Dio**：前者负责实际页面导航；后者作为统一 HTTP 客户端进入基础设施层。**v1.0 没有自建 API 地址，翻译和语言模型下载均不经过 Dio。** 不应为了让 Dio“有请求”而增加无业务价值的接口。

当前仓库是 Flutter 计数器模板，`pubspec.yaml` 只声明 Flutter、`cupertino_icons` 和测试依赖；下列目录、路由、数据库和服务均属于待实现内容。项目 Dart 约束为 `^3.12.2`，`README.md` 说明 Android 开发使用官方 Flutter 3.44.9。Android 工程目前使用 AGP 9.0.1、Kotlin 2.3.20，`compileSdk`、`minSdk`、`targetSdk` 仍读取 Flutter 默认值，正式集成时必须核对最终构建值。

## 2. 技术选型

| 责任 | 选型 | 首版使用方式 |
|---|---|---|
| UI | Flutter Material 3 | 主题、响应式布局、深色模式与系统组件 |
| 页面导航 | `go_router` | 四个底部页面和语言选择、离线语言包、隐私说明等次级页面 |
| 状态与依赖注入 | `flutter_riverpod` | 翻译状态、历史查询、设置、服务实例；使用 Riverpod 3 的 `Notifier`/`AsyncNotifier`，先不引入代码生成 |
| 离线翻译 | `google_mlkit_translation` | 模型查询、下载、删除与设备端翻译；封装在 `TranslationService` 中 |
| 语言识别 | `google_mlkit_language_id` | 自动检测；低置信度或短文本要求用户手选 |

| HTTP | `dio` | 提供受控的 `Dio` 实例和错误映射；首版不配置后端 URL、不发翻译请求 |
| 朗读 | `flutter_tts` | 原文与译文朗读；设备没有相应语音时显示提示 |
| 系统分享 | `share_plus` | 调用 Android 分享面板；复制使用 Flutter SDK 的 `Clipboard` |
| 隐私政策 | `url_launcher` | 打开正式公开政策 URL；应用内也提供政策文本或入口 |
| 版本信息 | `package_info_plus` | “关于”页面读取真实版本号和构建号 |
| 验证 | `flutter_test`、`integration_test` | 状态与组件测试、真机核心流程；`flutter_lints` 延续现有配置 |

## 3. 分层与依赖方向

```text
页面 / Widget
   │ 只观察状态并发出用户意图
   ▼
Riverpod Controller / Provider
   ├── TranslationService ── ML Kit Translation / Language ID
   ├── HistoryRepository ── sqflite
   ├── SettingsRepository ── sqflite
   ├── SpeechService ── flutter_tts
   └── ShareService ── Clipboard / share_plus

NetworkClient ── Dio（v1.0 预置，无翻译 API 消费者）
AppRouter ── go_router（只管导航，不承载业务状态）
```

业务页面不能直接实例化 ML Kit、Dio 或数据库。Controller 只依赖明确的服务接口或 Repository；插件细节限制在实现层。首版只为真正跨边界的能力定义接口，避免一层功能拆成多层空壳。

## 4. go_router 路由设计

采用 `StatefulShellRoute.indexedStack` 容纳四个底部入口，使用户切换页面时保留每个页面的导航栈。若实测内存或切换行为不合适，可退回普通 `ShellRoute`；翻译输入状态始终由 Controller 保存，不依赖 Widget 是否仍挂载。

| 路径 | 显示 | 导航位置 |
|---|---|---|
| `/translate` | 翻译首页 | 底部标签 1；初始路由 |
| `/translate?record=<id>` | 从历史重新查看记录 | 按 ID 读库并显示原文与译文 |
| `/history` | 历史与搜索 | 底部标签 2 |
| `/favorites` | 收藏列表 | 底部标签 3；复用记录表 |
| `/settings` | 设置 | 底部标签 4 |
| `/languages?mode=source` | 原文语言选择 | 从翻译页进入的次级页面 |
| `/languages?mode=target` | 本次翻译的目标语言选择 | 从翻译页进入 |
| `/languages?mode=default-target` | 默认目标语言选择 | 从设置进入，保存到设置表 |
| `/offline-models` | 离线语言包管理 | 从设置进入的次级页面 |
| `/privacy`、`/about` | 隐私说明、关于 | 从设置进入的次级页面 |

路由只传简单、可恢复的参数，如语言选择模式和历史记录 ID。`mode` 仅允许 `source`、`target`、`default-target`，其他值返回安全的默认状态。不要通过 `extra` 传唯一的数据副本，以免应用恢复或深链打开时丢失上下文。点击历史记录时跳转到带 `record` 查询参数的翻译页，由 Controller 按 ID 读库并加载原文、译文和实际语言代码。未知路径显示可返回首页的错误页。

## 5. 翻译状态与执行顺序

`TranslationController` 使用一个明确状态对象，不在 Widget 中散布多组布尔值：

```text
idle → detecting → checkingModel → downloadingModel → translating → success
                                           └───────────────────────────→ error
```

状态至少携带：输入文字、选定源语言、实际识别语言、目标语言、结果、当前阶段、可恢复错误和请求序号。输入为空时禁用翻译；文本上限先按计划设为 5000 字符，并在真机测试后调整。手动点击按钮执行翻译；输入变化时可用约 500 ms 的防抖更新识别提示，但不反复启动模型下载或翻译。发起新翻译后忽略旧请求的晚到结果。

执行步骤：

1. 校验非空和长度；如果源语言为“自动检测”，调用 Language ID。结果不可靠时提示手动选择。
2. 校验源语言与目标语言不同；`auto` 不允许作为目标语言。互换自动检测源语言时，采用最近一次实际识别语言；尚未识别则提示先选择。
3. 通过 ML Kit 模型管理器检查源/目标语言模型。缺少时显示“不确定进度”的准备状态并按 SDK 接口下载，不虚构百分比。
4. 下载失败时展示原因和显式“重试”；不无限自动重试。下载成功后创建 Translator，翻译完成或异常时释放其资源。
5. 翻译成功后写入本地历史并展示操作按钮；短时间内的同内容重复提交只保留一条。失败时保留输入，允许重试。

ML Kit 的模型是否已下载，以其模型管理器查询结果为准，**不在 SQLite 中维护第二份“已下载”标志**。UI 可以临时缓存查询结果，但重新进入管理页或下载/删除后必须刷新。语言代码内部统一用受支持的代码映射，不能靠中文展示名判断业务逻辑。

## 6. 本地数据库：sqflite

首版数据库版本从 1 开始。记录表同时承载历史与收藏；设置使用同一个数据库内的键值表。所有写入用参数绑定；搜索原文/译文先用转义通配符后的 `LIKE` 和排序，数据量变大后再考虑全文索引。

```sql
CREATE TABLE translation_records (
  id TEXT PRIMARY KEY,
  source_text TEXT NOT NULL,
  translated_text TEXT NOT NULL,
  source_language TEXT NOT NULL,
  target_language TEXT NOT NULL,
  is_favorite INTEGER NOT NULL DEFAULT 0,
  engine TEXT NOT NULL DEFAULT 'mlkit',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE INDEX idx_records_created_at
  ON translation_records(created_at DESC);
CREATE INDEX idx_records_favorite_created_at
  ON translation_records(is_favorite, created_at DESC);

CREATE TABLE app_settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

`source_language` 保存实际检测出的语言，而不是字符串 `auto`；`auto` 是首页选择状态。时间统一存 Unix 毫秒，读取时本地化显示。收藏只是 `is_favorite` 更新，删除历史记录时对应收藏一起删除，清空历史必须二次确认。`onUpgrade` 集中维护后续迁移，不删除用户数据库来规避迁移问题。

本地数据库并不自动等于“绝不离开设备”：Android Auto Backup 可能备份应用数据。发布前应核对 `allowBackup`、Android 12+ 的 `dataExtractionRules` 与旧版本备份规则，决定是否排除翻译历史及设置，并让隐私政策与实际行为一致。

## 7. Dio 网络层

首版将 Dio 放在 `core/network/` 并由 Riverpod 提供一个受控实例，便于未来增加明确获批的接口。建议集中配置连接/接收超时、统一 `DioException` 到应用错误的映射以及请求取消能力。**没有确定的服务器地址时不配置假 `baseUrl`，也不向占位域名发请求。**

| 场景 | 首版路径 |
|---|---|
| 输入文字翻译 | `TranslationService` → ML Kit；不经过 Dio |
| 语言模型下载 | ML Kit Model Manager；不能改用 Dio 直接下载模型文件 |
| 隐私政策网页 | `url_launcher` 打开公开 URL；不必用 Dio 抓取后再渲染 |
| 复制、分享、朗读 | Flutter 或系统能力；不经过 Dio |
| 将来接入后端 API | Feature Repository → NetworkClient → Dio；另立需求后才增加端点 |

Dio 不启用自动上传日志、请求体打印或未审查的拦截器；即使 Debug 日志也不得记录原文、译文或系统分享内容。翻译页面不能直接 `ref.read(dioProvider)` 发起请求。若未来增加云翻译，需要同步更新隐私政策、Data safety 和用户提示，不能在当前“设备端翻译”文案下悄悄上传文本。

## 8. 设备能力、合规与发布验证

- Android `minSdk` 目标 23；新应用提交 Google Play 时 `targetSdk` 目标至少 36，并核对 `compileSdk`。当前工程读取 Flutter 默认值，实施时显式验证最终值及 AAB Manifest。
- Google ML Kit Android 原生翻译/识别 API 要求最低 API 23；社区 Flutter 插件说明当前仍列 target/compile SDK 35。先在项目现有 AGP 9.0.1、Kotlin 2.3.20 和目标 API 36 下做真机 PoC，验证编译、首次下载、离线运行、模型删除和 Release 混淆。文档中的版本号不代表已通过这些验证。
- TTS 用设备语音服务，先检测语言可用性；按插件说明核对 Android 11+ 的 TTS 服务 `queries` 配置。相机、麦克风、定位、联系人和全盘存储权限均不在首版范围。
- ML Kit 输入文本在设备端处理，但 SDK 可能向 Google 获取模型/更新并传输性能与使用指标。正式隐私政策和 Play Data safety 必须依据最终依赖和 Manifest 如实填写；应用内也提供隐私政策入口。
- 正式结果页和商店资料按 ML Kit 翻译使用与归因要求核对。HTML 原型中的示例译文不能当作真实翻译效果或审核截图。
- 真机验证包含 API 23 附近设备和新系统：首次下载、无网重启、弱网失败重试、短文本识别、长文本、快速换语言、历史持久化、收藏、复制分享、TTS 缺失、深色模式、返回栈与 AAB 安装。
- 个人开发者账号进入 Production 的 Closed Testing 条件，仍按 Google Play Console 当前要求核验；本架构文档不表示已满足测试或上架条件。

## 9. 建议实施顺序与完成判定

1. **工具链 PoC**：确认官方 Flutter、API 36、AGP 9 与两个 ML Kit 插件可构建；真机完成英语 ↔ 中文、模型下载与离线翻译。如果社区插件受阻，只替换 `TranslationService` 实现，可用 Flutter Platform Channel 接原生 ML Kit。
2. **应用骨架**：建立 `ProviderScope`、主题、`MaterialApp.router`、四个底部页面及次级路由；加入 Dio Provider，但不增加虚构的 HTTP 端点。
3. **数据和主链路**：SQLite 建库、Repository、翻译 Controller、错误状态、历史/收藏/搜索；设置与默认语言入库。
4. **系统能力与上架**：TTS、复制分享、隐私/关于、备份策略、签名与 Release AAB、Play 测试轨道和真实测试反馈。

架构完成的判定不是“依赖能解析”，而是 Android Release 构建通过、真机核心路径可用、无网二次翻译可用、数据在重启后存在、失败可重试、隐私说明与实际行为一致。实现后运行 `flutter analyze`、`flutter test`，再在真机上执行上述检查。
