# 小安翻译 v1.0 第一版功能计划与开发文档

> 项目名称：小安翻译  
> Android 包名：`com.jbk.xiaoants`  
> 技术栈：Flutter / Dart  
> 第一阶段平台：Android  
> 文档版本：v1.0  
> 制定日期：2026-09-22  
> 第一阶段目标：尽快形成稳定可用的 Android 翻译应用，进入 Google Play Internal Testing / Closed Testing，并为后续 Production 上架做好准备。

---

## 1. 项目背景

当前 Google Play 开发者账号为个人开发者账号，注册时间约为 2025 年 8 月。现阶段项目的首要目标不是一次性做成跨平台大型翻译产品，而是：

1. 使用 Flutter 完成一个真实可用、可持续维护的 Android 翻译应用。
2. 尽快上传 Google Play 测试轨道，降低开发者账号因长期闲置而被关闭的风险。
3. 完成新个人开发者账号的 Closed Testing 要求。
4. 申请 Production Access，并正式发布到 Google Play。
5. Android 版本稳定后，再逐步扩展 OCR、语音、AI 以及 iOS / macOS / Windows。

### 1.1 当前 Google Play 约束

截至 2026-09-22：

- Google Play 新应用和应用更新需以 Android 16 / API 36 或更高版本为目标。
- 2023-11-13 之后创建的个人开发者账号，在申请 Production Access 前，需要进行 Closed Testing。
- 至少 12 名测试人员需要连续 14 天保持加入 Closed Test，才能申请 Production Access。
- Internal Testing 适合早期快速验证，Closed Testing 用于满足正式发布前的测试要求。
- 对于被标记为不活跃的开发者账号，Google 要求完成联系方式验证，并创建发布应用或发布现有应用更新；如果暂时不准备公开，可以使用 Internal Testing 或 Closed Testing。

因此，本项目第一阶段应优先保证：
**可构建、可安装、可翻译、无明显崩溃、可上传 Google Play 测试轨道。**

# 2. 产品定位

## 2.1 第一版定位

**一个简单、快速、无需登录、支持设备端离线翻译的多语言翻译工具。**

核心体验：

> 输入文字 → 自动识别语言 → 翻译 → 复制 / 分享 / 朗读 → 自动保存历史。

第一版不追求与 Google Translate、DeepL 做全面竞争，也不追求 AI 大模型能力。

重点是：

- 功能完整
- 使用简单
- 无需注册
- 不依赖自建服务器
- 尽量减少权限
- Google Play 审核风险低
- 代码架构能够继续扩展

# 6. 核心功能详细设计

## 6.1 文本翻译

### 用户流程

```text
用户输入文本
   ↓
选择或自动识别源语言
   ↓
选择目标语言
   ↓
检查对应语言模型
   ↓
未下载 → 下载模型
已下载 → 继续
   ↓
执行翻译
   ↓
展示结果
   ↓
保存历史
```

### 交互要求

- 输入为空时禁止执行翻译。
- 输入文本变化后，不立即频繁调用翻译。
- 建议使用 400～600ms debounce。
- 用户也可以点击“翻译”按钮主动执行。
- 正在翻译时显示 Loading。
- 新翻译开始时，应取消或忽略旧请求结果，避免结果错位。
- 翻译失败不能导致页面崩溃。

---

## 6.2 自动语言识别

使用 ML Kit Language Identification。

默认：

```text
源语言：自动检测
目标语言：中文
```

识别出英文：

```text
English → 中文
```

识别出中文且目标语言也是中文时，可以自动建议切换到英文，但第一版不建议强制替用户修改，避免产生不可预期行为。

### 注意

短文本，例如：

```text
OK
No
Apple
AI
```

语言检测可能不可靠。

因此必须始终允许用户手动指定源语言。

---

## 6.3 语言选择

第一版底层可支持 ML Kit 所支持的语言，但 UI 优先显示常用语言。

建议常用语言：

- 自动检测
- 简体中文
- English
- 日本語
- 한국어
- Français
- Deutsch
- Español
- Português
- Italiano
- Русский

语言选择页提供搜索。

内部统一使用 BCP 47 / ML Kit 对应语言代码，不在业务代码中到处使用中文名称判断。

示例：

```dart
class AppLanguage {
  final String code;
  final String name;
  final String nativeName;
}
```

## 6.4 语言互换

点击：

```text
中文 ⇄ English
```

执行：

```text
sourceLanguage ↔ targetLanguage
```

同时：

- 如果已有翻译结果，可以交换原文和译文。
- “自动检测”不能作为目标语言。
- 如果源语言是“自动检测”，点击交换时应使用最近一次实际识别出的语言；如果尚未识别，则提示用户先选择源语言。

# 7. 翻译历史

## 7.1 自动保存

每次翻译成功后保存：

- 原文
- 译文
- 源语言
- 目标语言
- 创建时间
- 收藏状态

避免相同内容在很短时间内重复写入。

---

## 7.2 数据模型

```dart
class TranslationRecord {
  final String id;

  final String sourceText;
  final String translatedText;

  final String sourceLanguage;
  final String targetLanguage;

  final DateTime createdAt;

  final bool favorite;
}
```

建议数据库表额外预留：

```text
engine
updatedAt
```

方便以后增加 AI / DeepL / 云同步，但第一版不必真正使用。

# 10. 离线语言模型管理

翻译使用 Google ML Kit On-device Translation。

特点：

- 设备端运行
- 支持 50+ 语言
- 语言模型按需下载
- 模型可以删除
- 无需自建翻译后端

## 10.1 首次使用语言

例如用户第一次：

```text
中文 → English
```

流程：

```text
检查中文/英语所需模型
   ↓
模型不存在
   ↓
显示“正在准备离线翻译模型”
   ↓
下载
   ↓
成功
   ↓
执行翻译
```

如果当前 Flutter 插件或原生 SDK 不提供可靠的字节级下载进度，不强行制作虚假的 `36% / 72%` 进度条，使用不确定进度 Loading 即可。

# 15. TranslationService 抽象

这是第一版最重要的架构设计之一。

UI 不允许直接：

```text
Page → ML Kit
```

必须：

```text
Page
 ↓
Provider / Controller
 ↓
TranslationService
 ↓
ML Kit
```

接口建议：

```dart
abstract interface class TranslationService {
  Future<String> translate({
    required String text,
    required String sourceLanguage,
    required String targetLanguage,
  });
}
```

ML Kit：

```dart
class MlKitTranslationService implements TranslationService {
  @override
  Future<String> translate({
    required String text,
    required String sourceLanguage,
    required String targetLanguage,
  }) async {
    // ML Kit implementation
    throw UnimplementedError();
  }
}
```

后续可以直接扩展：

```text
TranslationService
 ├── MlKitTranslationService
 ├── DeepLTranslationService
 ├── GoogleCloudTranslationService
 ├── GeminiTranslationService
 └── OpenAITranslationService
```

# 16. 翻译状态设计

建议统一：

```dart
enum TranslationStatus {
  idle,
  detectingLanguage,
  checkingModel,
  downloadingModel,
  translating,
  success,
  error,
}
```

页面只根据状态渲染。

不要在 Widget 中散落：

```text
isLoading
isDownloading
isDetecting
hasError
...
```

避免后期状态失控。

# 18. 数据与隐私设计

第一版原则：

- 不需要用户账号
- 不收集手机号
- 不收集邮箱
- 不上传翻译历史到自建服务器
- 不保存图片
- 不请求相机
- 不请求麦克风
- 不请求定位
- 翻译历史仅保存在设备本地

这样能显著降低：

- 隐私政策复杂度
- Google Play Data Safety 填写复杂度
- 权限审核风险

## 18.1 ML Kit 注意事项

ML Kit 设备端 Translation API 需要遵守 Google 的相关使用与归因要求。

正式提交 Google Play 前必须再次核对：

- Attribution 要求
- Data Safety 声明
- ML Kit 数据处理说明
- 当前版本 SDK 是否存在新增数据收集行为

# 22. Google Play 发布计划

## 阶段 A：Internal Testing

目标：

**尽快让 Play Console 中存在真正发布到测试轨道的版本。**

操作：

```text
AAB
 ↓
Internal Testing
 ↓
测试账号安装
 ↓
真实运行
```

检查：

- Play 安装正常
- App 签名正常
- ML Kit 正常
- 无崩溃

---

## 阶段 B：Closed Testing

个人账号注册于 2025 年，因此正式发布前需要满足新个人账号的测试要求。

计划：

```text
≥ 12 名测试人员
+
连续保持 opted-in ≥ 14 天
```

建议准备 15～20 人，避免有人退出导致人数跌破 12。

测试期间收集：

```text
测试人员
测试设备
测试日期
问题
修改结果
```

示例：

```text
问题：
用户第一次翻译时不知道正在下载模型。

修改：
增加“正在准备离线翻译模型”的明确提示。
```

这类真实反馈可以用于 Production Access 申请。

# 27. 第一版最终边界

第一版最重要的不是“功能多”，而是完成一个闭环：

```text
安装
 ↓
输入
 ↓
识别
 ↓
翻译
 ↓
复制 / 分享
 ↓
历史
 ↓
离线再次使用
```

同时满足：

```text
代码可维护
+
App 可测试
+
Google Play 可上传
+
Closed Testing 可执行
+
后续功能不用推倒重来
```

如果开发过程中出现功能取舍冲突，优先级始终按照：

```text
1. 稳定性
2. Google Play 可发布
3. 核心文本翻译体验
4. 错误处理
5. UI
6. 附加功能
```
